# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"UniClub" — a university club/community management frontend.

## Commands

Package manager is **bun** (`bun.lock` present, no `package-lock.json`/`yarn.lock`).

- `bun install` — install dependencies
- `bun run dev` — start Vite dev server
- `bun run build` — typecheck (`tsc -b`) then production build via Vite
- `bun run lint` — run oxlint
- `bun run preview` — preview the production build

There is no test runner configured in this repo (no test script, no test files).

## Architecture

- **Layout — feature-first**. Everything a feature owns (API calls, pages, components, hooks, labels) lives under `src/features/<feature>/`; cross-feature building blocks live under `src/shared/`. Imports **always** use the `@/` alias (→ `src/`, declared in both `tsconfig.app.json#paths` and `vite.config.ts#resolve.alias`) — no `../../` relative imports.

  ```
  src/
    features/
      auth/          api/{auth,users}.ts · context/AuthContext.tsx · hooks/useAuth.ts
                     guards/{ProtectedRoute,RequireManagement,RequirePermission,RequireRole}.tsx
                     authorization.ts · pages/{Login,Register,VerifyEmail,Profile,Forbidden}.tsx
      clubs/         api/clubs.ts · hooks/useClubRole.ts · labels.ts · coverGradient.ts
                     components/Club*Section.tsx, ClubFormModal.tsx · pages/{Clubs,ClubDetail}.tsx
      activities/    api/activities.ts · labels.ts · formatActivityDateTime.ts
                     components/ClubActivitiesSection.tsx · pages/{Activities,ActivityDetail}.tsx
      admin/         api/{universities,users,applications,clubs,advisors,moderation,rbac}.ts (+ index.ts barrel)
                     context/AdminScopeContext.tsx · rank.ts · useRankActor.ts
                     labels.ts · components/ (+ user-detail/ split modal) · pages/Admin*.tsx
      universities/  api/universities.ts · components/ · pages/AdminUniversit*.tsx
      notifications/ api/notifications.ts · socket.ts · queries.ts · labels.ts
                     context/NotificationsContext.tsx · components/NotificationBell.tsx
    shared/
      api/client.ts · hooks/{useCountUp,useCooldown}.ts · ui/
      types/{common,user,university,club,activity,rbac,notification}.ts
    layouts/ · pages/{Landing,Dashboard}.tsx · App.tsx · main.tsx
  ```

  Two conventions worth keeping: a feature's `api/` mirrors the backend doc's section order, and files over ~250 lines get split (see `admin/api/` and `admin/components/user-detail/` for the pattern — a thin shell composing self-contained sections).
- **Stack**: React 19 + TypeScript + Vite, React Router v7, TanStack Query v5, react-hook-form + zod (via `@hookform/resolvers`) for forms, axios for HTTP, Tailwind CSS 3 for styling.
- **Backend contract**: `docs/architecture/` altındaki `FRONTEND_*.md` ve `API.md` dosyaları **senkron kopyadır** — tek kaynak `../uniclub-backend/docs/` (integration + reference). Her dosyanın başındaki `> **Senkron kopya**` satırı kaynak yolunu ve backend commit SHA'sını taşır; sözleşme güncellemesi önce backend'de yapılır, sonra frontend'e kopyalanır. Senkron komutu (PowerShell, repo kökünden):
  ```powershell
  $sha = git -C ../uniclub-backend rev-parse --short HEAD
  # her eşleşme için: kaynak içeriğinin başına
  # "> **Senkron kopya** — Kaynak: `../uniclub-backend/docs/...` · Backend commit: `$sha`"
  # ekle → docs/architecture/<hedef>.md
  ```

  Eşleşmeler: `auth.md`→`FRONTEND_AUTH_RBAC.md`, `admin-panel.md`→`FRONTEND_YONETIM.md`, `notifications-and-limits.md`→`FRONTEND_BILDIRIM_VE_LIMITLER.md`, `clubs.md`→`FRONTEND_CLUBS.md`, `rank-and-platform.md`→`FRONTEND_RUTBE_VE_PLATFORM.md`, `activities.md`→`FRONTEND_ETKINLIKLER.md`, `announcements.md`→`FRONTEND_DUYURULAR.md`, `public.md`→`FRONTEND_KAMUYA_ACIK.md`, `reference/api.md`→`API.md`, `university.md`→`FRONTEND_UNIVERSITY.md`, `auth-guards.md`→`FRONTEND_AUTH_GUARD_GUIDE.md`, `mail-verification.md`→`MAIL_DOGRULAMA.md`, `operations/machine-setup.md`→`MAKINE_KURULUMU.md`, `tenant-settings.md`→`FRONTEND_TENANT_SETTINGS.md`. **Henüz senkronlanmadı** (ihtiyaç duyulduğunda alınacak): `dashboard.md`, `media.md`, `moderation.md`, `platform-panel.md`. **Konu rehberleri:** `FRONTEND_AUTH_RBAC.md` (auth + self-service), `FRONTEND_YONETIM.md` (9-rollü RBAC + `/api/admin` + `/api/auth` yönetim), `FRONTEND_RUTBE_VE_PLATFORM.md` (rank + platform hesapları), `FRONTEND_BILDIRIM_VE_LIMITLER.md` (WS bildirimler, 429, `EMAIL_NOT_VERIFIED`), `FRONTEND_CLUBS.md` (kulüpler), `FRONTEND_ETKINLIKLER.md` (etkinlikler/RSVP), `FRONTEND_KAMUYA_ACIK.md` (kamuya açık vitrin + afiş QR çözümleme), `FRONTEND_DUYURULAR.md` (duyuru yaşam döngüsü + zamanlanmış yayın), `FRONTEND_TENANT_SETTINGS.md` (tenant politika ayarları), `API.md` (tüm endpoint özet kataloğu). Roller/permission'lar için `FRONTEND_YONETIM.md` esas alınır (`FRONTEND_AUTH_RBAC.md` RBAC'ı oraya yönlendirir). Response envelope `{ success, message, data }`; tek istisna `POST /auth/login` (`user` + `token` kökte). `message` alanları `Accept-Language` ile çevrilir — kalıcı mantık için `code`/HTTP status kullan.
- **Tenant scope & platform accounts** (`FRONTEND_RUTBE_VE_PLATFORM.md` §1/§2): `user.universityId` is **`string | null`** — `null` means a *platform account* (`super_admin`, `platform_support`) that belongs to no university. **Never build an admin URL from `user.universityId`**; the target tenant comes from `useAdminScope()` (`src/features/admin/context/AdminScopeContext.tsx`), which reads `GET /api/admin/universities` — the only correct answer to "which universities can this user manage?". It returns 1 row for a tenant admin (no selector shown), N rows for a platform account (selector shown), 0 rows for an unscoped account. Tenant-bound admin pages wrap their content in `RequireUniversity` so no page can ever produce `/admin/universities/null/...`. The public `GET /api/universities` (`features/universities/api`) is deliberately global and is for the **registration form only** — using it in the panel leaks other universities into a `university_admin`'s view. Platform accounts cannot enter student self-service routes (backend returns 400); `RequireTenantAccount` redirects them from `/dashboard`, `/clubs`, `/profile` to `/admin`.
- **Role rank hierarchy** (`FRONTEND_RUTBE_VE_PLATFORM.md` §3/§4): every `Role` has a `rank` (0–100, higher = more powerful; seed: super_admin 100, platform_support 90, university_admin 60, `*_affairs` 45, moderator/auditor 30, advisor 20, student 10) and `GET /users/me/permissions` returns `maxRank`. The rule the backend enforces: **an actor may only touch roles/users strictly *below* their own rank** — equality is rejected, so nobody can act on themselves; `super_admin` is exempt from rank checks but **still cannot remove its own role**. Frontend mirrors this in `src/features/admin/rank.ts` (`rankOf`, `outranks`, `canManageUser`, `canAssignRole`, `canRemoveRoleFrom`, `canSetRoleRank` + Turkish reason strings) with the actor built by `useRankActor()`. These are UX only — disable + explain rather than let the user hit a 400.
- **Error semantics** (`FRONTEND_RUTBE_VE_PLATFORM.md` §5): business-rule violations (self-demotion, equal/higher rank, last super_admin, platform-role assignment, tenantless account in a student flow) return **400**, not 403. `403` is only *no permission* / *tenant scope violation* / *suspended account*. The `client.ts` interceptor must therefore keep logging out **only** on 401 and the 403 suspension message — do not generalize it to 403, or these 400 messages would be swallowed. Surface them with `getErrorMessage(error, fallback)`.

  Two responses now carry a machine-readable `code` (`FRONTEND_BILDIRIM_VE_LIMITLER.md` §2/§3) — **branch on `code`, never string-match `message`**: `403 + code: "EMAIL_NOT_VERIFIED"` (a `pending` account attempted a write) and `429 + code: "RATE_LIMITED"` (+ `Retry-After` in seconds). Read them with `getErrorCode(error)` / `getRetryAfterSeconds(error)` and the `ERROR_CODES` constant from `client.ts`. `EMAIL_NOT_VERIFIED` is a **third 403 that must not log out** — the interceptor checks the code *before* the suspension-message check (both are 403) and dispatches `auth:email-not-verified`, which `EmailNotVerifiedModal` (mounted once in `MainLayout`) turns into a resend prompt, so individual write mutations never handle it. For 429, lock the button with `useCooldown()` + `formatCooldown()` (`shared/hooks/useCooldown.ts`) seeded from `Retry-After`; it's UX only — the real limit is server-side and survives a page refresh. Limits are keyed by the *protected resource*, not IP: resend-verification 3/h **per e-mail**, login 10/15min **per account**, register 60/h per IP (campus NAT means one student must not lock out the whole university).
- **API layer**: one module per backend feature, colocated with its feature — `auth/api/auth.ts` (identity), `auth/api/users.ts` (self-service), `universities/api/universities.ts`, `clubs/api/clubs.ts`, `admin/api/` (tenant management, split per doc section: `users` §5.1, `applications` §5.2, `clubs` §5.3, `advisors` §5.4, `moderation` §5.5, re-exported from `admin/api/index.ts`), `admin/api/rbac.ts` (roles/permissions/claims), `notifications/api/notifications.ts` (bell list/unread-count/mark-read + WS ticket). All go through the shared `apiClient` axios instance in `src/shared/api/client.ts` (`baseURL` exported as `API_BASE_URL` — the WebSocket URL is derived from it, so there is one address in the codebase; attaches `Authorization: Bearer <token>` from `localStorage`). The response interceptor logs out (clears token + dispatches `auth:unauthorized`) on **401** *and* on the **403 instant-suspension** message (`"Hesabınız askıya alınmıştır…"`), but **only for requests that carried an Authorization header** (so a failed login doesn't trigger a global logout). Use `getErrorMessage(error, fallback)` from `client.ts` to surface backend messages (it also handles the zod-issue 400 body shape).
- **Auth session** (`src/features/auth/context/AuthContext.tsx`, mounted in `main.tsx`): token in `localStorage` under `"token"`. Session bootstrap: `GET /users/me` (full profile + university + department + **roles**; `GET /auth/me` is minimal), `GET /users/me/permissions` (**effective permission set + roles + account status** — the guard source of truth), and `GET /users/me/clubs`. Exposes `token`, `user` (`MeProfile`), `roleNames`, `permissions`, `status`, `clubMemberships`, `login()`, `logout()`, `hasRole()`, `hasPermission()`/`can()`, `isAdmin` (has any management permission → shows the admin panel), `isSuperAdmin`, `isPlatform` (super_admin/platform_support → cross-tenant selector), `clubRoleOf(clubId)`, plus `isPlatformAccount` (tenantless — `universityId === null`) and `maxRank` (rank ceiling for admin actions). Import via `@/features/auth/hooks/useAuth`, never from the context module directly, and never read `localStorage` in components.
- **RBAC — two independent layers**: Layer A global roles (**9-role model**: `super_admin`, `platform_support`, `university_admin` (formerly `admin`), `student_affairs`, `academic_affairs`, `content_moderator`, `auditor`, `advisor`, `student`; open list, runtime-editable) with **granular `resource.action` permissions** (read vs write split: `user.view`/`user.manage`, `club.view`/`approve`/`update`/`member.manage`/`delete`, `application.view`, `announcement.moderate`, `gallery.moderate`, `university.*`, `role.manage`, `permission.manage`); and Layer B per-club roles (`member`/`officer`/`president` via `clubMemberships`; only `status === "approved"` rows count — use `useClubRole`/`clubRoleOf`, never derive from global roles). **The effective-permission endpoint now exists** (`GET /users/me/permissions`), so AuthContext reads `permissions` straight from the response — decide UI visibility by **permission key** (`can("club.approve")`), not role name. `src/features/auth/authorization.ts` no longer resolves permissions; it only holds permission-group constants (nav grouping) and a couple of role-name checks (`isPlatformRole`, `isSuperAdminRole`, `CORE_ROLE_NAMES`). Turkish labels for roles/permissions/status live in `src/features/admin/labels.ts` (club-side labels in `src/features/clubs/labels.ts`). Route/UI guards live in `src/features/auth/guards/` (`RequirePermission.tsx`, `RequireManagement.tsx` for the admin shell, `RequireRole.tsx`, fallback `src/features/auth/pages/Forbidden.tsx`) and are UX only — the real check is always server-side.
- **Auth flows to preserve**: registration derives the university from the e-mail domain (no university picker); `pending` users can log in and see an "verify your e-mail" banner (rendered in `MainLayout`); `/verify?token=` is handled by `src/features/auth/pages/VerifyEmail.tsx` (uses `useQuery` so the single-use token isn't burned by StrictMode double effects); the link expires in 24h, so both that banner and the `/verify` failure screen offer `POST /auth/resend-verification` through `auth/components/ResendVerification.tsx` (`docs/architecture/MAIL_DOGRULAMA.md`) — that endpoint **always** returns 200 with one fixed message whether or not the account exists (anti user-enumeration), so render the backend message verbatim and never infer account existence from it; a resend invalidates the user's older tokens; no refresh token — a 401 anywhere logs the user out via the interceptor event. A `pending` account may log in and **read**, but every write (join a club, apply, post an announcement/gallery item) is refused with `403 EMAIL_NOT_VERIFIED`; changing your own profile/password stays allowed on purpose, so a user who mistyped their password can still fix it.
- **Realtime notifications** (`src/features/notifications/`, `FRONTEND_BILDIRIM_VE_LIMITLER.md` §4): one WebSocket per session, opened by `NotificationsProvider` (in `main.tsx`, **inside** `AuthProvider` — it needs the token and calls `logout()`). Auth is a **single-use, 60s ticket** from `POST /notifications/ws-ticket`, never `?token=<jwt>` (a JWT in a query string leaks into access logs, proxy logs and browser history) — fetch a fresh ticket on **every** (re)connect. `socket.ts` owns the three protocol rules: reply plain-text `"pong"` to `{"event":"ping"}` (else the server drops you at 90s), reconnect with exponential backoff **+ full jitter** (no thundering herd on server restart), and treat close code **4401** as terminal (log out, don't retry). The socket carries *"your data is stale"*, not data: each event maps to TanStack Query invalidations, so the bell badge can never drift from the server. `account.verified` refetches `["auth","me"]` + `["auth","permissions"]` — this is what finally clears the pending banner when the user opens the mail in **another tab** (the banner reads `status` from `useAuth()`, which comes from `/users/me/permissions`, not `user.status`). `account.suspended` logs out immediately. Notification `type` is an **open** list: `labels.ts` (`notificationIcon`, `notificationLink`) falls back to a generic bell + no link, never throws. Known gap: no push while the app is closed — WS only lives as long as the page does; Web Push (VAPID) would be a separate layer.
- **Routing** (`src/App.tsx`): `/` (public landing for anonymous visitors), `/login`, `/register`, `/verify` are public. Protected member routes (`/dashboard`, `/activities`, `/clubs`, `/profile`) nest under one `ProtectedRoute` guard wrapping `MainLayout`. The management panel (`/admin/*`) uses a separate `AdminLayout` shell gated by `ProtectedRoute` + `RequireManagement` (any management permission), with sidebar sections shown per granular permission: `AdminUsers` (users list; the detail modal is `admin/components/user-detail/` — a `UserDetailModal` shell composing `AccountStatusSection`, `DepartmentSection`, `GlobalRolesSection`, `ClubMembershipsSection`, `PermissionOverridesSection`, `EffectivePermissionsSection`, each owning its own mutation and sharing `useUserDetail.ts` for the query + invalidation), `AdminClubs`, `AdminUniversities`, `AdminRoles` (role catalog + per-role permission bundle), `AdminPermissions` (permission catalog). `/admin` → `AdminHome` redirects to the first section the user can see. Unmatched paths redirect to `/`.
- **Data fetching**: pages use TanStack Query (`useQuery`) directly, calling their feature's `api/*.ts` functions. Auth-related data must come from `useAuth()`, not page-local queries. Single global `QueryClient` in `main.tsx`; after mutating profile data, invalidate `["auth", "me"]` (see `Profile.tsx`).
- **Forms**: local zod schema per page, DTO inferred from it, wired with `react-hook-form` + `zodResolver`, submitting through the feature's `api/*.ts` function (see Login/Register/Profile). Follow this pattern for new forms.
- **Design system**: the theme lives in `tailwind.config.js` (semantic `brand`/`accent` scales — subdomain themes override only these; legacy `club.*` colors kept for compat; keyframes/animations, `shadow-glow`/`shadow-card`, `ease-spring`, fonts) and `src/index.css` (component classes: `btn-primary`/`btn-secondary`/`btn-ghost`/`btn-white`, `input-field`/`input-label`/`input-error`, `card`/`card-hover`, `glass`/`glass-dark`, `badge`, `chip`, `alert-*`, `text-gradient`, `link-nav`; plus 3D utilities and reduced-motion support). Reusable animated components in `src/shared/ui/` (`AuroraBackground`, `TiltCard`, `Reveal`, `Cube3D`, `PageLoader`, plus `Modal`, `ConfirmDialog`, `EmptyState`, `Icon`, `IconButton`). Use these classes/components instead of re-rolling raw utility strings. UI copy is Turkish — match this.
- **Types**: shared domain types live in `src/shared/types/`, split by domain — `common.ts` (`ApiEnvelope`), `user.ts` (`SafeUser` — note `universityId: string | null`, `MeProfile` — `university: University | null`, `Role` with `rank`, `RoleName`, `UserStatus`), `university.ts`, `club.ts` (`ClubRole`, `ClubMembership`, `ClubApplication`, club enums), `rbac.ts` (`GlobalPermission`, `Permission`, `RoleWithPermissions`, `PermissionOverride`, `EffectivePermissions`, `AdminUserListItem`, `AdminUserDetail`), `notification.ts` (`AppNotification`, `NotificationType` — open list, `NotificationPage` cursor page, `WsTicket`). They mirror the backend docs exactly. `index.ts` is a barrel: import everything from `@/shared/types`, but add new types to the matching domain file. Reuse these; don't redeclare local interfaces.
